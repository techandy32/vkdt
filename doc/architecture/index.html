vkdt · architecture guide

how a raw file becomes a picture

vkdt develops raw photos and video on the graphics card. Every image operation is a small GPU program, and the whole application is organised around one structure: a graph of those programs. This guide follows an image through that graph, then looks at each part of the code that makes it work.

src/pipe/module.h · src/pipe/modules/colour/ · src/gui/shd/gui.frag contents ↑

Where the numbers change meaning

The same pixel holds very different numbers along the graph. What they mean is written in two tags that travel with every buffer: which primaries the three channels refer to, and which curve the values are encoded with. Follow six colour patches from the sensor to the screen.

Metadata travels with the image
When sizes travel forward through the graph, every module receives a copy of its input's image metadata: black and white level, white balance, colour filter pattern, the camera matrix, a noise profile, exposure data, and the two colour tags. A module that changes what the data means patches the copy: demosaic clears the filter pattern, colour sets the tags to rec2020 and linear.
One working space
From colour onward everything is linear rec2020. Modules do not have to ask what they are looking at, and the interface draws its own widgets in the same space.
Other inputs declare themselves
A jpg arrives tagged with sRGB primaries and an sRGB curve. An exr is usually tagged rec2020, linear. colour reads the tags and undoes the curve, so the rest of the graph never knows the difference.
Leaving through a file
On export the display sink is replaced by an output module. colenc is placed in front of it when the file is 8-bit, or when you ask for anything other than linear rec2020. colenc converts to the primaries and curve you ask for; the export panel defaults to sRGB.
The monitor comes last
A small text file per monitor holds a gamma and a 3 × 3 matrix. The interface's fragment shader applies them to the whole window, then dithers to 8 or 10 bits. Without this file the shader assumes sRGB.
Thumbnails take a shortcut
They are stored with rec2020 primaries and an sRGB curve. The texture format tells the GPU to undo the curve while sampling, so inside the interface they are linear again.

src/pipe/module.h · src/pipe/node.h contents ↑

You edit modules, the GPU runs nodes

The graph exists twice. The module graph is what the .cfg file describes and what you see in the interface. The node graph is what actually executes: every node is one shader run, usually a single compute dispatch.

Each module turns itself into nodes through its create_nodes callback. A module without one becomes a single node running its main.comp shader; grade and exposure work this way. A module like llap builds a whole pyramid.

The number of nodes can depend on the image size, which is why nodes are only created once sizes are known. A graph may hold up to 100 modules and 2000 nodes.

Modules and nodes talk through connectors. A connector has a name, a type, a channel layout and a pixel format, for example output:write:rgba:f16. A * is a blank, filled in from the other end of the wire, so a module like exposure works on any buffer.

Names such as colour, rgba or f16 are tokens: up to eight characters packed into one 64-bit integer, so comparing two names is a single integer comparison. That is why no module, connector or parameter in vkdt has a name longer than eight characters.

src/pipe/graph.c · dt_graph_run() contents ↑

What one run of the graph does

Everything goes through one function, dt_graph_run. It takes a set of flags that say which stages are needed, so a small change skips the expensive setup. Choose what just happened and watch which stages run.

Note what does not happen when you move a slider: nothing is rebuilt and nothing is cached per module. The parameters are rewritten and the whole graph runs again on the GPU. vkdt relies on the full run being fast and does not cache intermediate results.

src/pipe/graph-run-nodes-record-cmd.h contents ↑

What the GPU is actually told

The record stage walks the sorted node list and writes one Vulkan command buffer. Every compute node adds the same short sequence. This list is all the GPU receives for a run; between sources and sinks, no per-pixel work happens on the CPU.

A dispatch covers the node's output in groups of 8 × 8 pixels, so a 6000 × 4000 node is 750 × 500 groups: one shader invocation per pixel. Images stay in one layout (GENERAL) for their whole life, which keeps the barriers between nodes simple.

Every shader finds its inputs in the same places:

set 0, binding 2addresses of storage buffers, for the few nodes that use themuniform bref_t

Start vkdt or vkdt-cli with -d perf and the time each node took on the GPU is printed after every run. The timestamps you see in the figure are how that is measured.

Two modules, draw and overlay, rasterise instead: their nodes record a draw call where the others record a dispatch.

src/pipe/alloc.c · src/pipe/graph-run-nodes-allocate.h contents ↑

A few blocks of memory, planned in advance

A 24-megapixel image stored as four 16-bit float channels takes about 190 MB. A graph with dozens of nodes cannot give every output its own buffer. So vkdt plans: it walks the nodes in execution order, puts each output into the first free gap that fits, and releases a buffer as soon as its last reader has run.

The walk only computes offsets. When it is finished, vkdt makes one vkAllocateMemory call per block and binds every image at its offset. There are four kinds of block: recyclable images, protected images, CPU-visible staging buffers and uniforms. No device memory is requested while frames are running.

Some buffers are protected from recycling: sources, sinks, and anything a later frame has to read again.

src/pipe/anim.h · src/pipe/connector.h contents ↑

Frames, keyframes and feedback

A graph has a frame count and a frame rate, stored as frames: and fps: lines in the .cfg. For video, timelapses and animated parameters, the interface advances the frame number and runs the graph again. Only the command buffer is re-recorded; nodes and memory stay as they are.

Keyframes store a parameter value at a frame number. Each time the frame number changes, vkdt interpolates float parameters between the two neighbouring keyframes: linearly, with ease in or out, smoothly, or as a step. Other parameter types switch at the keyframe, except the brush strokes of draw, which are interpolated too.

Feedback connectors carry a module's output from the previous frame into the current one. This is how frame accumulation, temporal denoising and simulations work. A feedback buffer exists twice. Each frame writes one copy and reads the other, then they swap.

src/fit/fit.c · src/pipe/modules/loss/ contents ↑

The graph as a function: vkdt-fit

A graph turns parameters into pixels, and it can be run thousands of times without a window. vkdt-fit uses that to search for parameter values. You name the parameters to vary and one target: a parameter that some module fills in with a measurement of the result.

Two modules produce such measurements. loss compares its input with a reference image and stores the mean squared difference. pick averages colours at chosen spots and stores them; in its difference mode it also stores how far they are from reference colours. Both reduce the image on the GPU and receive a handful of numbers through write_sink.

For each evaluation the candidate values are written straight into parameter memory and the graph runs with three flags: record, download, wait. Nothing is rebuilt, so an evaluation costs little more than the GPU work itself. The search respects the range of each parameter's slider, and when it ends the complete graph is printed as a .cfg with the fitted values.

A real use from the repository: the table of neutral filter settings for the film simulation module. A grey patch goes through filmsim into pick, and three parameters are varied until the picked colour matches the grey.

vkdt-fit -d none -g neutral-start.cfg \
  --param "filmsim:01:filter m" \
  --param "filmsim:01:filter y" \
  --param "filmsim:01:ev paper" \
  --target "pick:01:de76" \
  --nelder-mead \
  --config "param:filmsim:01:film:$f" "param:filmsim:01:paper:$p"

Gauss-Newton is the default search method. Adam and Nelder-Mead can be selected instead. The example above uses Nelder-Mead.

src/pipe/modules/exposure/ contents ↑

Inside a module

A module is a folder. The simplest ones contain no C code at all. exposure is three tiny text files and a shader. Drag the slider in the figure to follow one value from the interface into the shader.

When a module needs more than one shader, or has to touch files, it adds a main.c that exports callbacks. Every one of them is optional, and roughly one module in five exports none.

The build compiles every shader to SPIR-V (main.comp.spv) and every main.c to lib<name>.so. At startup vkdt scans the modules directory, reads the text files and loads the libraries. A new module is a new folder; there is no central list to add it to.

src/pipe/modules/<yours>/ contents ↑

Write your own module

Because a module is only a folder, adding one takes five small files and no change anywhere else. The example is a made-up module, desat, that fades a picture to grey. It follows exposure line for line, but it has not been compiled or run against vkdt, so treat it as a sketch.

When one shader is not enough, add a main.c with a create_nodes callback, and a flat.mk next to it (it may be empty, but the build rule expects it). This is the whole of create_nodes in ciediag, the chromaticity diagram. One node counts pixels into a histogram, a second turns the counts into a picture.

const int id_collect = dt_node_add(graph, module, "ciediag", "collect",
  module->connector[0].roi.wd, module->connector[0].roi.ht, 1, 0, 0, 2,
  "input",  "read",  "rgba", "f16",  dt_no_roi,
  "output", "write", "r",    "ui32", &module->connector[1].roi);
graph->node[id_collect].connector[1].flags = s_conn_clear;
const int id_map = dt_node_add(graph, module, "ciediag", "map",
  module->connector[1].roi.wd, module->connector[1].roi.ht, 1, 0, 0, 2,
  "input",  "read",  "r",    "ui32", dt_no_roi,
  "output", "write", "rgba", "f16",  &module->connector[1].roi);
dt_connector_copy(graph, module, 0, id_collect, 0);
dt_node_connect  (graph, id_collect, 1, id_map, 0);
dt_connector_copy(graph, module, 1, id_map, 1);
dt_node_add
Folder and shader name, then width, height and depth of the dispatch, push constants (none here), the number of connectors, and five values per connector. An output gets a size; an input says dt_no_roi and takes the size of whatever it is wired to.
dt_connector_copy
Ties a connector of the module to a connector of a node. Here the module's input is really the first node's input, and its output is the second node's output.
dt_node_connect
A wire between two nodes inside the module. Nobody outside ever sees it.

Common mistakes

Parameter order matters
Parameters are packed in file order and copied byte for byte into the uniform block. The order in params must match the fields of params_t, and the packing must already agree with GLSL's std140 rules: declare a vec4 as float:4 and stay away from vec3.
Includes need a build rule
Shaders are not scanned for #include. If yours pulls in another file, add one dependency line to flat.mk so it is rebuilt when that file changes.
Check the wiring first
vkdt-cli --dump-modules and --dump-nodes print the graph in graphviz format, before and after modules expand into nodes.

src/pipe/modules/{filmcurv,llap,denoise,grade}/ contents ↑

Four modules, four formulas

The architecture exists to run small pieces of image maths. Here are four of them, taken from the shaders of the default graph. Move a slider and the curve is recomputed from the same formula the shader uses.

hilite
Builds a pyramid of the half-size raw image. Each coarser level averages only neighbours that are not clipped. On the way back up, a clipped pixel takes the coarse colour, scaled to agree with the channels the finer level still trusts. About 22 nodes for a 24-megapixel raw.
demosaic
Three methods. The default fits a small oriented gaussian to the greens of each block and interpolates green along it, then fills red and blue as ratios to green. RCD is an alternative for Bayer sensors. Half size merges each block into one pixel.
crop
One node. For every output pixel it rotates, applies a perspective transform solved from four corner points, and samples the input there.
hist
Two nodes. The first scatters: every input pixel adds one to a counter in a 1000 × 600 image, the three channels packed into one 32-bit integer with ten bits each. The second turns the counts into brightness.

src/gui/main.c contents ↑

The application around the graph

The GUI is a plain loop on the main thread. After a parameter change it does not wait for the image: the graph is submitted to the GPU's compute queue and the loop carries on drawing the interface. A later turn of the loop picks up the finished picture. The loop only blocks when a source has to be uploaded, a sink downloaded, or the graph rebuilt.

Four views, one graph
files browses and imports, lighttable shows thumbnails, darkroom edits one image, nodes shows the same graph as boxes and wires. The darkroom and the node editor share one graph object, so you can switch freely.
Widgets come from text
The darkroom reads each module's params.ui and draws the matching widget: slider, combo box, colour wheel, crop and perspective tools, about twenty-five widget types in all.
Colour-managed last
A display sink expects linear rec2020. The interface's own fragment shader converts to the monitor's profile at the very end, for the image and the widgets alike.
Thumbnails are graphs too
Two pool workers each own a graph and a work queue. They run an image's .cfg into the o-bc1 module and store a GPU-compressed, gzipped file that the lighttable can upload without converting the pixels.
One graph, one thread
A graph is only ever run by one thread at a time. A pool with one worker per CPU core handles thumbnails, exports, file copies and audio playback.
Full resolution by default
The darkroom processes every pixel of the image, zoomed in or not. A level-of-detail setting reduces the processed resolution. A second setting applies only while a slider is being dragged.
Headless is the same code
vkdt-cli -g photo.cfg --format o-jpg sets up Vulkan without a window, loads the same graph and swaps the display sink for a file output.

src/pipe/graph-history.h contents ↑

Undo is a replay

The darkroom keeps a history of your edits, and it is made of the same text lines as everything else. Nothing is stored about how to reverse an edit. To go back, vkdt resets the graph and replays the lines up to the point you chose.

The history lives in memory only. The history panel (ctrl-h) can also compress the list into a plain description of the current graph, roll back to the file on disk, or reset to the default graph.

src/core/threads.c · src/qvk/qvk.h contents ↑

Threads and GPU queues: who runs what

vkdt starts one pool of worker threads, one per CPU core, and asks the GPU for up to five queues. Each graph is run by one thread at a time and normally submits to one queue. Each queue has a lock, so two threads never submit to the same queue at once.

src/db/thumbnails.c contents ↑

How the lighttable gets its pictures

A thumbnail is the image's own graph, run small. Nothing special is stored for it and nothing can go out of date unnoticed: if the .cfg is newer than the cached thumbnail, the thumbnail is rendered again.

Half a byte per pixel
Thumbnails are stored in BC1, a block format that graphics cards sample directly. On disk the file is gzipped as well; once unpacked, the blocks are uploaded without conversion, and hundreds of thumbnails fit into the default 16 MB of GPU memory.
Least recently used
The cache has a fixed number of slots, 21 per MB. When all are taken, the slot the loader touched longest ago is reused. If the memory runs out before the slots do, the whole cache is dropped and rebuilt at twice the size.
Leaving the darkroom is cheaper
The picture is already on the GPU, so vkdt shrinks the display image with a small shader and writes the thumbnail from that. The graph is not run again.
Failures are visible
If a thumbnail cannot be rendered, its cache file becomes a link to a stock picture of a bomb, so the lighttable shows that something went wrong.

src/db/ contents ↑

Your folder is the database

There is no library file and no import step. vkdt opens a directory and works with what is there. Originals are never written to and never moved.

~/Pictures/harbour/              any folder you point vkdt at
├─ IMG_0412.CR2                  your original, never modified
├─ IMG_0412.CR2.cfg              sidecar: the complete graph for this image
├─ IMG_0412.CR2_01.cfg           a duplicate: a second edit of the same file
└─ vkdt.db                       ratings, labels, sort order and filter for this folder

~/.config/vkdt/
├─ config.rc                     settings
├─ presets/*.pst                 your presets
└─ tags/sunset/<hash>.cfg        symlinks to sidecars: a tag is a folder too

~/.cache/vkdt/
└─ <hash>.bc1                    thumbnails, stored GPU-compressed

An image without a sidecar gets a default graph. vkdt picks the input module from the file extension and starts from bin/default-darkroom.i-raw, or the matching file for jpg, video and the other inputs.

Ratings and labels belong to the folder, not to the image. A tag is a directory of symlinks with its own vkdt.db, so you can open it like any folder and rate the same pictures differently there.

A preset (.pst) uses the same line format as a .cfg but is a fragment: its lines are applied on top of the current graph, adding modules, rewiring and setting parameters.

Useful targets
make debug builds without optimisation and switches on the Vulkan validation layers. make sanitize adds the address sanitizer. make install copies binaries, modules and data under lib/vkdt/ below the prefix.
Toolchains
C for nearly everything, with clang as the default compiler. C++ only for the exr and MotionCam modules and the optional rawspeed loader, Rust for raw loading, and glslangValidator for shaders. Required libraries are Vulkan, glfw, libjpeg and zlib.
Where files are looked up
Defaults, presets and data are looked up in the graph's own folder first, then in ~/.config/vkdt, then next to the executable. Putting a file of the same name in your config folder overrides the shipped one.

Words the code uses

module
One image operation as the user sees it: a name, an instance, connectors and parameters.
node
One shader run. Modules create nodes; the GPU only ever sees nodes.
connector
An input or output of a module or node, with channels and a pixel format.
source · sink
Connectors where data enters or leaves the graph: files by way of the CPU, the display by a GPU copy.
roi
Region of interest. The size a buffer could have (full_wd, full_ht) and the size actually computed (wd, ht).
token
A name of up to eight characters stored in a 64-bit integer.
feedback
A connection that delivers last frame's output to this frame.
dspy
A module's optional diagnostic output, such as a curve plot. The darkroom wires it to a temporary display:dspy sink while that module is selected.
